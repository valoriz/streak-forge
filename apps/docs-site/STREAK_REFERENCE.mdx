## 1. What is Streak.js?

Streak.js is a **Bun/TypeScript static site generator**. Pages are described declaratively in `streak.sitemap.json`, rendered from small, isolated pieces (a layout + widgets + a data handler), and shipped as plain HTML with opt-in client interactivity.

**Important correction from earlier docs: Streak.js v2 does not use React.** Widgets and layouts are written in JSX, but that JSX compiles through Streak's **own** minimal JSX runtime (`streak-forge/jsx-runtime`, backed by `src/jsx/element.ts` and `src/jsx/renderToString.ts`) — a plain function that returns a lightweight VNode tree, rendered once to an HTML string on the server. There is no VDOM diffing, no reconciler, no hooks, and no client-side hydration of any kind. `useState`, `useEffect`, etc. simply do not exist in this runtime — a widget that imports them from `react` would either fail to resolve or be inert. This is enforced by the project's own ESLint rule (`no-hooks-in-widgets`, see [§21](#21-eslint-configuration)).

Key properties:
- **No client framework ships by default** — widgets render to plain HTML strings; nothing hydrates
- **Widget-driven** — pages are assembled from small, independent functions called *widgets*
- **Data flows through handlers, not props drilling** — an optional `Middleware.ts`, an optional `CommonHandler.ts`, and a per-page data handler run in that order before anything renders (see [§14](#14-the-render-pipeline))
- **Two runtime modes**:
  - `streak-forge dev` — a live server that renders every request fresh, with hot reload
  - `streak-forge build` — renders every page in `streak.sitemap.json` once and writes an intermediate JSON snapshot per page to `out/`. Publishing this output live is handled by **Nexus** — see the [Nexus documentation](https://docs.nexusoneonline.com/) for details.
- **Progressive enhancement** — client interactivity is opt-in via the `Script` component

The CLI tool is `streak-forge`. The npm package is also named **`streak-forge`** (not `streak`), and components are imported from **`"streak-forge/components"`**.

## 2. Mental Model

```
streak.sitemap.json                    ← page registry: one entry per URL
        │
        ▼
Middleware.ts (optional)                ← runs first, for every URL resolution
  (url, req?) => RenderConfig | undefined
  undefined = fall through to the sitemap's own entry for this URL
        │
        ▼
CommonHandler.ts (optional)             ← shared data, computed once per build
  () => {...}                             (or fresh on every dev request)
        │
        ▼
dataHandler(metadata, { common })       ← src/handlers/YourHandler.ts
  async fn → { WidgetId: data, ... }
        │
        ▼
rootLayout()                            ← src/layouts/YourLayout.tsx
  full <html> document with WidgetPlaceholder slots
        │
        ▼
each widget({ data: dataHandlerOut[id] })  ← src/widgets/*.tsx
  plain functions; render to an HTML fragment
        │
        ▼
styles collected (non-destructively) + widgets injected into layout slots
        │
        ▼
dev:   live HTML response, HMR-injected
build: out/<url>/<version>/raw-content.json  (an intermediate snapshot —
       see §14; Nexus turns this into the published site)
```

**Nothing renders at runtime in the browser by default.** The browser receives finished HTML; any interactivity you want has to be explicitly wired up with `Script`.

```
│
├── .prebuild/                    # streak-forge pre-build output (gitignored)
│

    └── <url>/
        └── <version>/
            └── raw-content.json  # one intermediate snapshot per page
```

**Important rules:**
- `streak.sitemap.json` must be at the project root
- Handler filenames must match `dataHandler` in the sitemap (no extension)
- `CommonHandler.ts` and `Middleware.ts` are **reserved, auto-discovered filenames** inside `src/handlers/` — they are found by name, not referenced from the sitemap
- Layout filenames must match `rootLayout` in the sitemap (no extension)
- Widget filenames must match `widgets[].type` in the sitemap (no extension)
- A widget/handler/layout may also be a folder containing an `index.ts(x)`/`index.js(x)` file instead of a single file — both are discovered the same way
- Files inside `public/` are served statically under `/`
- `out/` and `.prebuild/` are build artifacts — never edit files there

## 4. streak.sitemap.json

The **central registry** for all pages. Every page that Streak resolves statically must have an entry here (pages resolved dynamically by `Middleware.ts` do not need one — see [§7](#7-middlewarets--custom-route-resolution)).

```json
[
  {
    "url": "/",
    "renderConfig": {
      "renderId": "homeRenderId",
      "metadata": { "pageName": "home", "seoTitle": "Hello Streak — Home" },
      "dataHandler": "HomeDataHandler",
      "rootLayout": "MainLayout",
      "widgets": [
        { "id": "PageHead",      "type": "PageHead"      },
        { "id": "HelloNav",      "type": "HelloNav"      },
        { "id": "HelloBanner",   "type": "HelloBanner"   },
        {
          "id": "HelloFeatures",
          "type": "HelloFeatures",
          "loadingStrategy": "lazy"
        }
      ],
      "version": "1.0.0"
    }
  }
]
```

### Field reference

| Field | Type | Description |
|---|---|---|
| `url` | `string` | The URL path this page is served/built at — the sitemap is loaded into a `Map<url, entry>` |
| `renderId` | `string` | Identifier for this render, carried through into the build output and progress reporting |
| `metadata` | `object` | Free-form per-page data. Passed as the **first argument** to your `dataHandler`, and as the props object to your `rootLayout` component |
| `dataHandler` | `string` (optional) | Filename of the data handler in `src/handlers/`, **without extension**. If omitted, no data handler runs and widgets receive `data: undefined` |
| `rootLayout` | `string` | Filename of the layout in `src/layouts/`, **without extension** |
| `widgets[]` | `array` | Ordered list of widgets to render into this page |
| `widgets[].id` | `string` | Identifies which slice of handler data to pass as `props.data`, and links to the matching `WidgetPlaceholder` |
| `widgets[].type` | `string` | Identifies the widget filename in `src/widgets/`, **without extension** |
| `widgets[].loadingStrategy` | `"lazy"` \| omitted | If `"lazy"`, the widget's JS/HTML fragment loads after the page becomes interactive (dev only — see [§13](#13-loading-strategies)) |
| `version` | `string` | Written into the build output path as `out/<url>/<version>/raw-content.json` |

### Critical rules

- `id` and `type` in `widgets[]` are independent:
  - `id` links to the handler return object key **and** the matching `WidgetPlaceholder`'s `id`
  - `type` links to the widget component filename **and** the matching `WidgetPlaceholder`'s `type`
  - They are usually the same string but don't have to be
- Each `id` must be unique within a page's `widgets[]` (it keys the handler data slice and the placeholder). The same `type` may appear in multiple entries on one page — that's how the same widget component is placed in more than one slot; each such entry still needs its own unique `id` and its own `WidgetPlaceholder`
- `<Script>` ids are deduplicated per page, so a widget `type` used more than once on a page must emit a distinct `<Script id>` per instance or only the first instance's client script ships
- Every widget listed in `widgets[]` must have a corresponding `WidgetPlaceholder` in the layout whose `id` and `type` equal that entry's `id` and `type` (this is placeholder-to-entry matching, not `id` == `type`)
- The sitemap loader validates each entry has `url`, `renderConfig`, `renderConfig.renderId`, `renderConfig.rootLayout`, and `renderConfig.widgets[]` — a missing field throws at load time (both `dev` and `build`)

## 5. Data Handlers

A data handler is a **default-exported async function** with the signature:

```typescript
(metadata?: Record<string, unknown>, ctx: { common?: Record<string, any> }) => Promise<Record<string, any>>
```

- `metadata` is exactly the sitemap entry's own `metadata` object for this page
- `ctx.common` is whatever `CommonHandler.ts` returned (`undefined` if there's no `CommonHandler.ts`, or on any page where it returned nothing)

```typescript
// src/handlers/HomeDataHandler.ts

interface CommonData {
  branding?: { logoSrc?: string; logoAlt?: string; tagline?: string };
  nav?: { links?: { label: string; href: string }[] };
}

const getHomeData = async (
  metadata?: Record<string, unknown>,
  { common }: { common?: CommonData } = {},
) => {
  console.info("[HomeDataHandler] received metadata:", metadata);

  return {
    status: 200, // conventional, but see note below — not required or read by the framework

    PageHead: {                // key matches widgets[].id === "PageHead"
      title: "My Site",
      description: "Built with Streak.js",
    },

    HelloNav: {
      logoSrc: common?.branding?.logoSrc ?? "/images/streak-logo.svg",
      links: common?.nav?.links ?? [{ label: "Home", href: "/" }],
    },
  };
};

export default getHomeData;
```

### Rules

- Must be `export default` — Streak imports it by default export
- Must be `async` (or return a Promise)
- Return value is an object whose keys are matched against `widgets[].id`; each widget receives `{ data: yourReturnValue[widgetId] }` as props
- You can call APIs, read files, query databases — any async operation is allowed
- The handler filename (without `.ts`) must match `dataHandler` in `streak.sitemap.json`

### `status`, `notFound`, and what the framework actually reads

Earlier docs (and the convention widely copied across handler files) say a handler "must" return `{ status: 200, ... }`. In v2, **`status` is not read or required by the framework at all** — it's a leftover convention. The only special top-level key the pipeline inspects is:

- **`notFound`** — if a data handler's return value has a truthy `notFound` field, the build pipeline marks that page's render as `notFound: true` in its output snapshot.

Everything else at the top level that isn't `common` or a widget `id` is simply not used — `streak-forge build` filters the handler's return value down to only `common` (passthrough) and the declared widget ids before writing it to `raw-content.json`. `streak-forge dev` (the live server) does **not** filter — it passes the handler's whole return value straight through, so a stray top-level field is harmless there too, just unused by widgets that don't declare it as their `id`.

### How widget data flows

```
Handler returns:
{
  status: 200,
  HelloBanner: { heading: "Hello", accentColor: "#818cf8" }
}

Widget receives:
props = { data: { heading: "Hello", accentColor: "#818cf8" } }

// Access in widget:
const heading = props?.data?.heading ?? "Default";
```

### Timing and timeouts

Every handler call (data handler, `CommonHandler`, `Middleware`) is wrapped in a timeout **warning**, not a hard timeout — it never gets cancelled. If a handler takes longer than 1000ms, a yellow warning is logged; past 2000ms it starts logging escalating red errors every 2000ms until it resolves. This is purely diagnostic output for spotting a slow API call during a build or a slow dev request — the promise is always awaited to completion.

## 6. CommonHandler.ts — Shared Data Across Pages

`CommonHandler.ts` is a **reserved, auto-discovered filename** inside `src/handlers/`. It is entirely optional — if the file doesn't exist, nothing changes for any other handler; `common` is simply `undefined` everywhere.

```typescript
// src/handlers/CommonHandler.ts

const getCommonData = async () => {
  console.info("[CommonHandler] fetching shared site data...");

  return {
    branding: {
      logoSrc: "/images/streak-logo.svg",
      logoAlt: "Streak.js",
      tagline: "The React static site generator.",
    },
    nav: {
      links: [
        { label: "Home",   href: "/" },
        { label: "Docs",   href: "#" },
        { label: "GitHub", href: "#" },
      ],
    },
  };
};

export default getCommonData;
```

### Signature and rules

```typescript
() => Promise<Record<string, any> | undefined>
```

- **No arguments** — unlike a page data handler, `CommonHandler` receives nothing
- Its return value is threaded into **every** page's data handler as `ctx.common`
- **`streak-forge build`**: called **exactly once** for the entire build, and that single result is reused for every page — this is the whole point of the file: put API calls here that would otherwise be repeated by every page's own handler (site branding, global nav, feature flags, etc.)
- **`streak-forge dev`**: called **fresh on every single request**, never cached — a live dev server should never serve stale common data
- Wrapped in the same handler-timeout warning as any other handler (see [§5](#5-data-handlers)); a slow `CommonHandler` blocks every page that depends on it

Use it for data that's genuinely the same across pages. If a page needs its own unique data, put that in the page's own handler instead — `CommonHandler` output is shared verbatim, not merged or overridden per page.

## 7. Middleware.ts — Custom Route Resolution

`Middleware.ts` is a **reserved, auto-discovered filename** inside `src/handlers/`. It is entirely optional — if the file doesn't exist, URL resolution behaves exactly as if it weren't there (the sitemap's own entry for a URL is used, or a 404/no-match otherwise).

```typescript
// src/handlers/Middleware.ts
import { readFileSync } from "fs";
import { join } from "path";

// Same shape as a streak.sitemap.json entry - see §4 for the full field reference.
interface SitemapEntry {
  url: string;
  renderConfig: Record<string, unknown>;
}

let sitemapCache: SitemapEntry[] | undefined;
const loadSitemap = (): SitemapEntry[] => {
  if (!sitemapCache) {
    const sitemapPath = join(import.meta.dir, "../../streak.sitemap.json");
    sitemapCache = JSON.parse(readFileSync(sitemapPath, "utf-8")) as SitemapEntry[];
  }
  return sitemapCache;
};

// Maps a trigger URL -> the streak.sitemap.json url whose render config it
// should use instead.
const routeMap: Record<string, string> = {
  "/page-2": "/",           // an already-listed sitemap URL, overridden here
  "/dynamic/test": "/",     // NOT in streak.sitemap.json at all — "any route"
};

const resolveMiddleware = async (url: string, _req?: Request): Promise<RenderConfig | undefined> => {
  const targetUrl = routeMap[url];
  if (!targetUrl) return undefined;

  const targetEntry = loadSitemap().find((entry) => entry.url === targetUrl);
  return targetEntry?.renderConfig;
};

export default resolveMiddleware;
```

### Signature and rules

```typescript
(url: string, req?: Request) => Promise<RenderConfig | undefined>
```

- `url` is the path being resolved (`url.pathname`)
- `req` is the real `Request` object **only in `dev`** — during `build`, `Middleware` is called with just the sitemap's own `url` for that page and no `req`
- Return `undefined` to **skip** — fall through to the sitemap's own entry for that URL (or a 404 in `dev` / no page built in `build`, if there isn't one)
- Return a full `RenderConfig` object to **use that instead** — this is what makes two things possible:
  1. Overriding a URL that **is** already in `streak.sitemap.json` with a different page's config
  2. Serving a URL that **is not** in `streak.sitemap.json` at all — a genuine "any route" / catch-all mechanism
- Runs **first**, before `CommonHandler` and before the page's own `dataHandler`, on every single resolution attempt:
  - In `dev`: on **every request**
  - In `build`: **once per sitemap page**
- Wrapped in the same handler-timeout warning as any other handler — a slow `Middleware` blocks the page it's resolving

The `RenderConfig` type it returns is the same shape as a sitemap entry's `renderConfig` field (see [§4](#4-streaksitemapjson)) — `{ renderId, metadata?, dataHandler?, rootLayout, widgets[], version, notFound? }`.

## 8. Layouts

A layout is a **default-exported function** that returns a full HTML document. It uses `WidgetPlaceholder` to mark where widgets are injected. It is **not** a React component — it's a plain function rendered once through Streak's own JSX runtime; no hooks, no client behavior.

```tsx
// src/layouts/MainLayout.tsx
import { WidgetPlaceholder } from "streak-forge/components";

const MainLayout = () => {
  console.info("Rendering Main Layout");
  return (
    <html dir="ltr" lang="en">
      <head>
        <WidgetPlaceholder id="PageHead" type="PageHead" />
      </head>
      <body className="bg-white text-gray-900 antialiased">
        <WidgetPlaceholder id="HelloNav"      type="HelloNav"      />
        <WidgetPlaceholder id="HelloBanner"   type="HelloBanner"   />
        <WidgetPlaceholder id="HelloFeatures" type="HelloFeatures" />
        <WidgetPlaceholder id="HelloFooter"   type="HelloFooter"   />
      </body>
    </html>
  );
};

export default MainLayout;
```

### Rules

- Must be `export default`
- Receives the sitemap entry's `metadata` object as its props (`{}` if `metadata` was omitted)
- Must render a complete `<html>` document (not a fragment)
- Every widget listed in `streak.sitemap.json`'s `widgets[]` array must have a matching `WidgetPlaceholder` in the layout
- `WidgetPlaceholder` `id` and `type` must exactly match the sitemap entries
- The layout filename (without `.tsx`) must match `rootLayout` in the sitemap

## 9. Widgets

A widget is a **default-exported function** that receives `props.data` from the handler and returns a JSX fragment. Like layouts, widgets are plain functions rendered once on the server — not React components, no state, no hooks.

```tsx
// src/widgets/HelloBanner.tsx
import { Preload, Script } from "streak-forge/components";

type HelloBannerProps = {
  data?: {
    heading?: string;
    accentColor?: string;
    animationMs?: number;
  };
};

const HelloBanner = (props: HelloBannerProps) => {
  // Always use optional chaining + nullish coalescing for safety
  const heading     = props?.data?.heading     ?? "Hello, World.";
  const accentColor = props?.data?.accentColor ?? "#818cf8";
  const animationMs = props?.data?.animationMs ?? 700;

  return (
    <section id="hello_banner">
      <h1>{heading}</h1>

      <Preload href="/styles/tailwind.css" as="style" media="" />

      <Script id="hello-banner-script" options={{ accentColor, animationMs }}>
        {(gDom: any, options: any) => {
          const section = document.getElementById("hello_banner");
          if (section) {
            section.style.opacity = "0";
            section.style.transition = `opacity ${options.animationMs}ms ease`;
            requestAnimationFrame(() => { section.style.opacity = "1"; });
          }
        }}
      </Script>
    </section>
  );
};

export default HelloBanner;
```

### Rules

- Must be `export default`
- Props type must follow the `{ data?: YourType }` pattern
- Always use `??` defaults — `data` may be `undefined` if the handler doesn't return that key
- Widget filename (without `.tsx`) must match `type` in the sitemap and `type` in the layout's `WidgetPlaceholder`
- Widgets are **stateless** — there is no client-side re-render, no hooks, ever. This is enforced at lint time by the `no-hooks-in-widgets` rule (see [§21](#21-eslint-configuration))

### Optional: `skeleton` export

A widget file may also export a **named** `skeleton` function alongside its default export, with the same `{ data }` props signature:

```tsx
export const skeleton = (props: HelloBannerProps) => (
  <div className="animate-pulse h-96 bg-gray-100 rounded-2xl" />
);

export default HelloBanner;
```

When a widget uses `loadingStrategy: "lazy"` or is nested inside a `Dynamic` block, `dev` renders a placeholder `<div>` in the widget's spot until the real content is fetched. If `skeleton` is exported, its rendered output fills that placeholder; otherwise a bare hidden `<span>` is used. This lets you show a real loading skeleton instead of empty space before lazy content resolves.

## 10. streak-forge/components API

Import from `"streak-forge/components"`:

```tsx
import { WidgetPlaceholder, Script, Dynamic, Preload } from "streak-forge/components";
```

There are exactly four components. Internally, each one just builds a small marker element (`<widget>`, `<script>`, `<dynamic>`, `<preload>`) that a later processing step turns into the real HTML.

### 10.1 WidgetPlaceholder

**Used in: layouts only**

Marks a slot where a widget is injected.

```tsx
<WidgetPlaceholder id="HelloBanner" type="HelloBanner" />
```

| Prop | Type | Description |
|---|---|---|
| `id` | `string` | Links to the widget `id` in the sitemap and the handler return key |
| `type` | `string` | Links to the widget component filename in `src/widgets/` |

Both props are required — an empty `id` or `type` throws at render time.

### 10.2 Script

**Used in: widgets only**

Injects a `<script>` tag into the page. The child function's source is baked directly into the page and executed as `((fnSource)(window, options))`.

```tsx
<Script id="my-widget-script" options={{ color: accentColor, delay: animationMs }}>
  {(gDom: any, options: any) => {
    // This runs in the browser — not on the server
    // gDom is literally `window` — extended with a few Streak-added methods (§11)
    // options = the object passed to the options prop above
    const el = document.getElementById("my-element");
    if (el) el.style.color = options.color;
  }}
</Script>
```

| Prop | Type | Description |
|---|---|---|
| `id` | `string` | Unique script tag id |
| `options` | `object` | **The only bridge from server to browser.** Serialized to JSON and inlined into the emitted `<script>` tag |
| `children` | `function` | `(gDom, options) => void` |
| `nonce` | `string` (optional) | CSP nonce, passed straight through to the `<script nonce>` attribute |

#### Critical rules for Script

1. **`options` is the ONLY bridge from server to browser.** The function body is baked into the page as source text — it cannot close over variables from the widget's function scope.

   ```tsx
   // WRONG — closure variable doesn't survive serialization
   const color = props?.data?.color ?? "#fff";
   <Script id="x">
     {() => { document.body.style.color = color; /* color is undefined! */ }}
   </Script>

   // CORRECT — pass via options
   const color = props?.data?.color ?? "#fff";
   <Script id="x" options={{ color }}>
     {(gDom: any, options: any) => { document.body.style.color = options.color; }}
   </Script>
   ```

2. **No imports inside Script.** The script runs in a plain browser context.

3. **`gDom` is `window`**, extended with a small set of helper methods (see [§11](#11-gdom--the-browser-client-runtime)).

4. **Always type `gDom` and `options` as `any`** in TypeScript — they exist only at browser runtime.

5. A build-time transform statically finds and flags **closure leaks**: any identifier referenced free inside a `Script` body that is neither a known browser global (`window`, `document`, `fetch`, `Math`, …), nor `gDom`, nor `options`, is reported — as a console warning + a live dismissible overlay in `dev` (over the same HMR stream used for reload), or as a hard failure from `streak-forge validate` (see [§16](#16-cli-commands-and-build-scripts)). This is what catches the mistake in rule #1 above before it ships broken to the browser.

6. The generated script looks roughly like:
   ```html
   <script id="my-widget-script">((function(gDom, options){
     /* your function body here, already transpiled to plain JS */
   })(window,{"color":"#818cf8","delay":700}));</script>
   ```

### 10.3 Dynamic

**Used in: widgets only**

Wraps content that should be **absent from the initial HTML** and injected on demand.

```tsx
<Dynamic id="my-panel">
  <div id="my-panel-content" style={{ opacity: 0 }}>
    <p>This content is NOT in the initial static HTML.</p>
  </div>
</Dynamic>
```

Then trigger injection from a `Script`:

```tsx
<Script id="my-script">
  {(gDom: any) => {
    const btn = document.getElementById("show-btn");
    btn?.addEventListener("click", () => {
      gDom.loadDynamicComponent("my-panel", () => {
        // Called after the content is injected into the DOM
        const el = document.getElementById("my-panel-content");
        if (el) requestAnimationFrame(() => { el.style.opacity = "1"; });
      });
    });
  }}
</Script>
```

| Prop | Type | Description |
|---|---|---|
| `id` | `string` | Identifies this `Dynamic` block — used as the argument to `loadDynamicComponent` |
| `children` | node | Content to defer |

#### How Dynamic works internally (dev)

1. When a widget's rendered HTML is assembled into the page, any `<Dynamic id>` block found inside it is pulled out — its inner HTML and any `<script>` tags it contained are stored server-side (keyed by page URL + id), and a skeleton placeholder `<div>` is left in its place
2. This extraction happens **regardless of whether the parent widget itself is eager or `lazy`** — a `Dynamic` block nested inside a lazy widget still becomes independently fetchable once the lazy widget's own HTML lands
3. `gDom.loadDynamicComponent(id, callback)` fetches that stored content from the dev server and swaps it into the placeholder
4. The `callback` fires after injection — use it to trigger CSS transitions

`streak-forge build`'s output snapshot does **not** perform this extraction step at all — it captures each widget's raw rendered HTML with the `<dynamic>`/`<script>`/`<preload>` marker tags still embedded, untouched. Turning that raw snapshot into a finished page (placeholder extraction, lazy/dynamic splitting, script injection) is exactly what `dev` does live, and what Nexus does for published output.

#### Dynamic vs `loadingStrategy: "lazy"`

| | `Dynamic` | `loadingStrategy: "lazy"` |
|---|---|---|
| Initial HTML | Content **removed** | Content **present**, HTML is not deferred — only its JS load timing is |
| When injected | On `loadDynamicComponent()` call | Sequentially, right after the page loads |
| Use case | Heavy/conditional content, gated behind user interaction | Below-the-fold widgets, non-blocking JS |

### 10.4 Preload

**Used in: widgets and layouts**

Emits a `<link rel="preload">` tag to hint the browser to fetch a resource early.

```tsx
<Preload href="/styles/tailwind.css" as="style" media="" />
<Preload href="https://example.com/hero.jpg" as="image" media="(min-width: 768px)" />
<Preload href="/fonts/Inter.woff2" as="font" media="" />
```

| Prop | Type | Description |
|---|---|---|
| `href` | `string` | URL to preload |
| `as` | `string` | Resource type: `"style"` \| `"image"` \| `"font"` \| `"script"` \| `"video"` |
| `media` | `string` | Media query — `""` means all screens |

`Preload` only emits a hint tag — you still need the actual `<link>` or `<img>` tag in your markup elsewhere.

## 11. gDom — The Browser Client Runtime

`gDom` is literally **`window`**, with a small runtime attached to it. It's passed as the first argument to every `Script` function, and the same methods are also just available as `window.xxx` anywhere else in a page's client-side code.

This is the **complete** API — there is no Web Worker involved anywhere in this runtime, and no cookie/session/first-visit tracking of any kind.

```typescript
// Append a real <script src> or <link rel=stylesheet> tag to document.body,
// deduped by src — a second call with the same src reuses the same promise
// instead of loading it again.
gDom.addResourceToBody(
  src: string,
  options?: { async?: boolean },
  callback?: () => void,
): void

// Fetches a file from /assets/<name> via addResourceToBody. Resolves once
// the <script>/<link> tag has loaded.
gDom.loadPackage(name: string): Promise<void>

// Fetches a <Dynamic id="..."> block's stored HTML/scripts and swaps it
// into that block's placeholder element.
gDom.loadDynamicComponent(id: string, callback?: () => void): void

// Fetches a lazy widget's stored HTML/scripts and swaps it into its
// placeholder element. Same underlying fetch mechanism as loadDynamicComponent.
gDom.addWidgetToBody(id: string, callback?: () => void): void
```

That's the entire public surface. There is no `onVisible`, `debounce`, `geById`, `stall`, `setCookie`, `getCookie`, or `window.ftr` — none of these exist in v2's client runtime. If you need an `IntersectionObserver`, a debounce, or a cookie helper, write it yourself inside your `Script` body (or load it via `loadPackage`, see [§12](#12-loadpackage--loading-third-party-assets)) — nothing is provided for you.

### After loadPackage resolves

`loadPackage` just appends a real `<script>` tag and waits for its `onload` — whatever global variable that script sets on `window` is then available on `gDom` too, since `gDom` **is** `window`:

```typescript
gDom.loadPackage("js/motion.js").then(() => {
  const { animate, scroll, inView, stagger, spring } = (gDom as any).Motion;
  // now use Motion.js APIs
});
```

## 12. loadPackage — Loading Third-Party Assets

`loadPackage` loads a third-party JS or CSS file **directly into the page** — a plain `<script>`/`<link>` tag appended to `document.body`. There is **no Web Worker, no message-passing protocol, and no off-main-thread fetch** involved anywhere in this path.

### How it works

```
gDom.loadPackage("js/motion.js")
    │
    ▼ calls gDom.addResourceToBody("/assets/js/motion.js", { async: true }, callback)
    │
    ▼ addResourceToBody looks at the file extension:
    │     .js  → creates a <script src="..." async> tag
    │     .css → creates a <link rel="stylesheet" href="..."> tag
    │   and appends it to document.body
    │
    ▼ the tag's real onload/onerror settles the returned Promise
    │
    ▼ Promise resolves
    │     window.Motion (or whatever global the file sets) is now available
```

Repeat calls to `addResourceToBody` (and therefore `loadPackage`) with the same `src` reuse the same in-flight/settled promise instead of injecting a duplicate tag — there's a simple `Map` of `src → Promise` for that, held on `window`.

### How to use it

```tsx
<Script id="my-animated-script" options={{ duration: 0.65 }}>
  {(gDom: any, options: any) => {
    gDom.loadPackage("js/motion.js")
      .then(() => {
        const { animate } = (gDom as any).Motion;
        animate("#my-element", { opacity: [0, 1] }, { duration: options.duration });
      })
      .catch((err: unknown) => {
        console.error("Failed to load motion.js:", err);
      });
  }}
</Script>
```

### File placement

The asset path `"js/motion.js"` maps to `public/assets/js/motion.js`.

```
Your project:
  public/assets/js/motion.js   ← commit this file to the repo

Fetched by the browser as:
  GET /assets/js/motion.js
```

**Do not gitignore `public/assets/js/*.js`** — these files are committed by developers and served as static assets, exactly like the rest of `public/`.

## 13. Loading Strategies

### Default (no `loadingStrategy`)

The widget's HTML is part of the normal page assembly, and any `Script` inside it loads/runs as part of the normal page load.

### `"lazy"`

```json
{ "id": "HelloFeatures", "type": "HelloFeatures", "loadingStrategy": "lazy" }
```

In `dev`, a `lazy` widget's rendered HTML/scripts are stored server-side and a skeleton placeholder is emitted in its place inside the initial response. The injected client runtime reads the list of lazy widget ids off a `<script id="w-m" type="application/json">` element and fetches them one at a time, in order, right after the page loads — see [§15](#15-client-runtime-internals) for the exact mechanism.

Use `"lazy"` for:
- Below-the-fold sections
- Heavy interactive widgets that don't need to block the initial response
- Anything you're fine showing a skeleton for briefly

### `Dynamic` component (not a loading strategy)

`Dynamic` removes content from the initial HTML entirely and only fetches it on an explicit `loadDynamicComponent()` call — this is a separate, opt-in mechanism from `loadingStrategy`, not a variant of it (see comparison table in [§10.3](#103-dynamic)).

## 14. The Render Pipeline

There is no fixed multi-stage "build pipeline" module chain in v2 — rendering one page is a straight-line async function (`buildPageData` for `build`, `renderPage` for `dev`), with `Middleware`/`CommonHandler` resolved just before it. Both entry points share the same core steps; they differ in what happens **after**.

### Steps common to every page render

1. **Middleware** (if a `Middleware.ts` exists) resolves the URL — see [§7](#7-middlewarets--custom-route-resolution). `dev`: on every request, with the real `Request`. `build`: once per sitemap page, no `Request`.
2. **CommonHandler** (if a `CommonHandler.ts` exists) runs — see [§6](#6-commonhandlerts--shared-data-across-pages). `build`: once for the whole run. `dev`: fresh every request.
3. **Data handler** runs as `dataHandler(metadata, { common })`, if the resolved config declares one.
4. **Layout renders** — the layout function is called with `metadata` as its props and rendered to an HTML string via Streak's own `renderToString`.
5. **Every widget renders** — each widget function is called with `{ data: dataHandlerOut[widget.id] }` as props and rendered to an HTML string. If the widget exports `skeleton`, that's rendered too (see [§9](#9-widgets)).
6. **Styles are collected, non-destructively** — every `<style>` and `<link rel="stylesheet">` tag found in the layout's and each widget's rendered HTML is scanned; local stylesheet files are read from disk and their contents concatenated into one combined string. The original `<style>`/`<link>` tags are left exactly where they were — nothing is stripped at this step.

### What happens next diverges

**`streak-forge dev`** (live, per-request):
7. The layout HTML, with each `<widget>` placeholder tag replaced by its real widget's assembled fragment, is post-processed (see [§15](#15-client-runtime-internals)): `<dynamic>` blocks are extracted to a fetchable placeholder, lazy widgets are extracted the same way, `<preload>` tags become real `<link rel=preload>` tags moved into `<head>`, and eager `<script>` tags plus the client runtime + widget registry are appended before `</body>`.
8. The finished HTML string is returned directly as the HTTP response (with the HMR client script injected if hot reload is enabled). **Nothing is written to disk in `dev`.**

**`streak-forge build`** (once per sitemap page):
7. None of the `dev` post-processing above runs. The raw layout HTML and each widget's raw HTML/skeleton HTML — **`<widget>`/`<dynamic>`/`<script>`/`<preload>` marker tags still embedded, unprocessed** — plus the collected `completeStyle` string, are bundled into one JSON object (a `RawContent` snapshot: `{ renderId, metadata, dataHandler, rootLayout, version, notFound?, widgets[], dataHandlerOut, rootLayoutOut, completeStyle }`).
8. That JSON is written to **`out/<url>/<version>/raw-content.json`**.

Publishing this raw snapshot as a live site — turning it into finished, optimized HTML, hosting it, routing it — is handled by **Nexus**. See the [Nexus documentation](https://docs.nexusoneonline.com/) for details; it's out of scope for this reference.

## 15. Client Runtime Internals

This section covers what actually ships to the browser and runs on page load in **`dev`** (this is also, conceptually, what a finished/published page produced from a `build` snapshot ends up doing — but the finishing step itself belongs to Nexus, not to this reference).

### The core runtime script

A small, real (not pseudocode) function is stringified and inlined into every rendered page:

```javascript
(function (win, opts) {
  win.__streakLoaded = win.__streakLoaded || new Set();
  win.__streakLoadedResources = win.__streakLoadedResources || {};

  win.addResourceToBody = function (src, options, callback) { /* §11 */ };
  win.loadPackage = function (name) { /* §12 */ };

  const applyContent = (type, id, data, callback) => {
    // Replaces the outerHTML of [component-id][component-type] with data.html,
    // then appends any of data.scripts as real <script id> tags on document.body.
    // Deduped via win.__streakLoaded so repeat calls are no-ops.
  };

  const fetchContent = (type, id, callback) => {
    // GET /__streak/content?page=<pathname>&type=<type>&id=<id>
    // then applyContent(...)
  };

  win.loadDynamicComponent = (id, callback) => fetchContent("c", id, callback);
  win.addWidgetToBody      = (id, callback) => fetchContent("w", id, callback);

  // Reads the lazy-widget id list out of the w-m element and fetches them
  // one at a time, in order, right away.
  const lazyWidgetIds = JSON.parse(
    win.document.getElementById(opts.widgetMetaId)?.textContent || "[]"
  );
  const loadNext = ([first, ...rest]) => {
    if (!first) return;
    win.addWidgetToBody(first, () => loadNext(rest));
  };
  loadNext(lazyWidgetIds);
})(window, { endpoint: "/__streak/content", widgetMetaId: "w-m" });
```

### The `w-m` element

```html
<script type="application/json" id="w-m">["HelloFeatures", "HelloAnimated"]</script>
```

A flat JSON array of lazy widget ids — nothing more. The core runtime script above reads it once on page load and fetches each one in sequence.

### Content fetching

Both `loadDynamicComponent` and `addWidgetToBody` go through the exact same request shape:

```
GET /__streak/content?page=<url-encoded pathname>&type=<w|c>&id=<url-encoded id>
```

`type` is `"w"` for a lazy widget, `"c"` for a `Dynamic` block. The response is `{ id, html, scripts: [{ id, content }] }`; `html` replaces the placeholder element (matched by `[component-id="<id>"][component-type="<type>"]`), and each entry in `scripts` becomes a new `<script id>` tag appended to `document.body`.

### Placeholder elements

Before a lazy widget or `Dynamic` block loads, its slot in the DOM looks like:

```html
<div component-placeholder component-type="w" component-id="HelloFeatures">
  <!-- widget's exported `skeleton`, rendered — or a hidden <span> if none -->
</div>
```

### Hot reload (dev only)

A second, small script connects to `/__streak_hmr` over Server-Sent Events:
- `reload` event → `location.reload()`
- `script-warning` event → renders a dismissible overlay banner at the bottom of the page reporting a `<Script>` closure leak (see [§10.2](#102-script)), pushed live over the same SSE connection used for reload — not a separate channel

This is injected only when hot reload is enabled (the default; disable with `STREAK_HMR=false`).

## 16. CLI Commands and Build Scripts

### Commands

`streak-forge` has exactly these public commands:

```bash
streak-forge dev          # live dev server + file watcher + hot reload
streak-forge pre-build     # optional: pre-bundles widgets/handlers/layouts for faster builds
streak-forge build         # renders every sitemap page, writes out/<url>/<version>/raw-content.json
streak-forge validate      # static check: <Script> closure leaks (hard fail if any found)
```

#### `streak-forge dev`

- Registers the `<Script>` transform (closure-leak scan + pre-serialization) and a JSX-compile step, applied to every module import from then on
- Starts an HTTP server (default port **3690**, override with `PORT`)
- Per request: resolves `Middleware` → `CommonHandler` → the page's data handler → layout + widgets → assembles the full page (see [§14](#14-the-render-pipeline)/[§15](#15-client-runtime-internals)) → returns HTML, with the HMR client injected
- Any path that doesn't resolve to a page falls through to serving a matching file from `public/` directly, or a 404
- Starts a file watcher over the whole project: on any `.ts`/`.tsx`/`.js`/`.jsx`/`.json`/`.html`/`.css` change, it busts that file's module cache entry, re-scans changed `.tsx`/`.jsx` files for `<Script>` closure leaks (broadcasting warnings), and broadcasts a reload event over the HMR stream

#### `streak-forge pre-build`

Optional performance step — bundles every discovered widget/handler/layout into standalone, minified JS under `.prebuild/` (via `Bun.build`, using the same `<Script>` transform), one output file per component. Also copies `streak.sitemap*.json`, `public/`, and `package.json` (as `app-package.json`) into `.prebuild/`. Wipes and recreates `.prebuild/` on every run.

This cache is **only** consulted when `READ_FROM_PREBUILD=1` is set — otherwise `dev`/`build` read straight from `src/` even if `.prebuild/` exists.

#### `streak-forge build`

- Loads `streak.sitemap.json`
- Resolves `CommonHandler` **once**, shared across every page
- For each sitemap page: resolves `Middleware`, runs the (possibly middleware-overridden) render pipeline, writes `out/<url>/<version>/raw-content.json`
- A single page failing is logged and counted, not fatal to the whole run — the process exits with code 1 only if at least one page failed
- Publishing this output live is handled by Nexus — see the [Nexus documentation](https://docs.nexusoneonline.com/) for details

#### `streak-forge validate`

Scans every `.tsx`/`.jsx` file under `src/widgets/` and `src/layouts/` for `<Script>` closure leaks (the same check `dev` only warns about live) and exits with code 1 if any are found — the CI-friendly hard-fail counterpart to the dev-time warning.

> Don't confuse this with a project's own `bun run validate` script, if it has one — that's project-authored tooling, not part of the `streak-forge` CLI. See [§23](#23-hello-streak-app--complete-annotated-example) for `hello-streak-app`'s example.

```json
    "moduleDetection":  "force",
```

- `strict: true` — all strict checks enabled; use `any` intentionally inside `Script` functions
- `noEmit: true` — TypeScript here is for type-checking only; Bun/the `streak-forge` CLI handle actually compiling/running your code

## 20. Testing with bun:test

Bun ships a built-in Jest-compatible test runner. No extra packages needed.

```typescript
// src/tests/HomeDataHandler.test.ts
import { describe, test, expect, beforeAll } from "bun:test";
import getHomeData from "../handlers/HomeDataHandler";

let data: Awaited<ReturnType<typeof getHomeData>>;

beforeAll(async () => {
  // No metadata/common needed for a basic shape test — both args are optional.
  data = await getHomeData();
});

describe("HomeDataHandler — top-level shape", () => {
  test("contains all required widget keys", () => {
    const keys = ["PageHead", "HelloNav", "HelloBanner", "HelloFeatures"];
    for (const key of keys) {
      expect(data).toHaveProperty(key);
    }
  });
});

describe("HomeDataHandler — HelloBanner", () => {
  test("accentColor is a valid hex string", () => {
    expect(data.HelloBanner.accentColor).toMatch(/^#[0-9a-fA-F]{3,8}$/);
  });

  test("animationMs is positive", () => {
    expect(data.HelloBanner.animationMs).toBeGreaterThan(0);
  });
});
```

To test how a handler reacts to `common` data, pass a fixture directly (there's no need to run `CommonHandler` for this — just shape the second argument yourself):

```typescript
const data = await getHomeData(
  { pageName: "home" },
  { common: { branding: { logoSrc: "/test-logo.svg" } } },
);
expect(data.HelloNav.logoSrc).toBe("/test-logo.svg");
```

### Test patterns

- **Handler tests**: Import the handler, call it (optionally with `metadata`/`{ common }` fixtures), assert on the return value's shape, types, non-empty strings, valid hex colors, ID uniqueness, numeric ranges
- **Widget helper tests**: Extract pure logic from widgets (validation, defaults, formatters) into standalone functions and test those independently
- **No DOM tests**: Widgets render to static HTML strings server-side — test handler data integrity instead

## 22. Common Errors and Fixes

### Error: 404 GET /images/hero.webp

**Cause:** Handler returns an image path that doesn't exist in `public/images/`.

**Fix:** Either add the file, or remove the field from the handler return value. Don't reference files you haven't placed in `public/`.

---

### Error: TypeError: Cannot read properties of undefined (reading 'progress')

**Cause:** Using Motion.js `scroll()` with the callback form in an incompatible version:

```typescript
// WRONG — y is undefined in some Motion.js versions
scroll(({ y }) => {
  animate("#bar", { scaleX: y.progress }, { duration: 0 });
});
```

**Fix:** Use the **linked animation form**, which drives the animation directly from scroll:

```typescript
// CORRECT
scroll(animate("#bar", { scaleX: [0, 1] }));
```

---

### Error: TypeError: Cannot read properties of undefined (reading '0') at inView.margin

**Cause:** Passing `{ margin: "-40px 0px" }` as the third argument to `inView()`.

```typescript
// WRONG
inView("#grid", callback, { margin: "-40px 0px" });
```

**Fix:** Omit the `margin` option entirely:

```typescript
// CORRECT
inView("#grid", callback);
```

---

### Error: loadPackage resolves but window.Motion is undefined

**Cause:** The file at `public/assets/js/motion.js` doesn't exist, or doesn't set `window.Motion`.

**Fix:**
1. Ensure `public/assets/js/motion.js` exists (committed to the repo, not gitignored)
2. Verify the file sets `window.Motion = { animate, scroll, inView, stagger, spring }`

---

### Error: console warning "references '<name>', which is not a browser global, gDom, or options"

**Cause:** A `<Script>` body reads a variable that was never passed through `options` — a closure leak, caught by the build-time scan described in [§10.2](#102-script).

```tsx
// WRONG — the_color is a server-side variable, not available after serialization
const the_color = props?.data?.color ?? "#fff";
<Script id="x">{() => { el.style.color = the_color; }}</Script>
```

**Fix:** Pass all server values through `options`:

```tsx
const the_color = props?.data?.color ?? "#fff";
<Script id="x" options={{ color: the_color }}>
  {(gDom: any, options: any) => { el.style.color = options.color; }}
</Script>
```

Run `streak-forge validate` to catch every instance of this across the project before shipping — it's the same check, run as a hard-fail CLI command instead of a dev-time warning.

---

### Error: Widget renders but shows no data / wrong data

**Cause:** Mismatch between the widget `id` in the sitemap and the key name in the handler return.

**Fix:** Make sure they match exactly. If the sitemap has `{ "id": "HelloBanner" }`, the handler must return `{ HelloBanner: { ... } }`.

---

### Error: Build succeeds but a widget is missing from the output

**Cause:** Widget is in the sitemap's `widgets[]` but has no `WidgetPlaceholder` in the layout with a matching `id` and `type`.

**Fix:** Add `<WidgetPlaceholder id="MyWidget" type="MyWidget" />` to the layout at the correct position.

---

### Middleware.ts — route overrides + a catch-all

```typescript
// src/handlers/Middleware.ts
import { readFileSync } from "fs";
import { join } from "path";

// Same shape as a streak.sitemap.json entry - see §4 for the full field reference.
interface SitemapEntry {
  url: string;
  renderConfig: Record<string, unknown>;
}

let sitemapCache: SitemapEntry[] | undefined;
const loadSitemap = (): SitemapEntry[] => {
  if (!sitemapCache) {
    const sitemapPath = join(import.meta.dir, "../../streak.sitemap.json");
    sitemapCache = JSON.parse(readFileSync(sitemapPath, "utf-8")) as SitemapEntry[];
  }
  return sitemapCache;
};

// "/page-2" is already a real sitemap URL — overridden to render "/" instead.
// "/dynamic/test" is NOT in streak.sitemap.json at all — this is what makes
// it resolve anyway ("any route").
const routeMap: Record<string, string> = {
  "/page-2": "/",
  "/dynamic/test": "/",
};

const resolveMiddleware = async (url: string, _req?: Request): Promise<RenderConfig | undefined> => {
  const targetUrl = routeMap[url];
  if (!targetUrl) return undefined;

  const targetEntry = loadSitemap().find((entry) => entry.url === targetUrl);
  return targetEntry?.renderConfig;
};

export default resolveMiddleware;
```

### HelloAnimated.tsx — Script + loadPackage (Motion.js)

Uses all seven Motion.js demos from the real app: scroll-linked progress bar, header entrance, a morphing headline sequenced via `.finished` promise chains, staggered card entrance with `inView`, 3D tilt-on-hover, a magnetic button, and cursor-following background orbs. The full widget is reproduced verbatim in `apps/hello-streak-app/src/widgets/HelloAnimated.tsx`; the interactivity is wired up like this:

```tsx
import { Script } from "streak-forge/components";

<Script id="hello-animated-script" options={{ animationDuration, words }}>
  {(gDom: any, options: any) => {
    gDom.loadPackage("js/motion.js")
      .then(() => {
        const { animate, scroll, inView, stagger, spring } = (gDom as any).Motion;

        // 1. Scroll progress bar — linked animation form, NOT the callback form
        scroll(animate("#scroll-bar", { scaleX: [0, 1] }));

        // 2. Header entrance
        animate("#animated-header", { opacity: [0, 1], y: [-30, 0] }, {
          duration: options.animationDuration, easing: "ease-out",
        });

        // 3. Morphing headline — .finished promise chain for sequencing
        const morphEl = document.getElementById("morph-word");
        const words: string[] = options.words ?? [];
        let wordIndex = 0;
        const morphNext = () => {
          wordIndex = (wordIndex + 1) % words.length;
          animate(morphEl, { opacity: 0, y: -20 }, { duration: 0.22, easing: "ease-in" })
            .finished
            .then(() => {
              if (morphEl) morphEl.textContent = words[wordIndex] ?? "";
              return animate(morphEl, { opacity: 1, y: 0 }, {
                duration: 0.55,
                easing: spring({ stiffness: 180, damping: 16, restSpeed: 0.5 }),
              }).finished;
            })
            .then(() => setTimeout(morphNext, 2200));
        };
        if (morphEl && words.length > 1) setTimeout(morphNext, 2200);

        // 4. Staggered card entrance — inView with NO third (margin) argument
        inView("#cards-grid", () => {
          animate(".tilt-card", { opacity: [0, 1], y: [70, 0], scale: [0.86, 1] }, {
            delay: stagger(0.13), duration: 0.9,
            easing: spring({ stiffness: 110, damping: 13, restSpeed: 0.5 }),
          });
        });

        // 5–7. 3D tilt on hover, magnetic button, cursor-following orbs —
        // see the real widget file for the full listeners.
      })
      .catch((err: unknown) => console.error("[HelloAnimated] motion.js failed to load:", err));
  }}
</Script>
```

### Motion.js API notes (for Streak context)

| API | Correct usage | Wrong usage (causes crash) |
|---|---|---|
| `scroll()` | `scroll(animate(el, {...}))` — linked form | `scroll(({ y }) => { y.progress })` — callback form with `y.progress` |
| `inView()` | `inView(el, callback)` — no third argument | `inView(el, cb, { margin: "-40px" })` — crashes on string margin |
| `animate().finished` | Use for sequencing — returns a Promise | Don't mix with `async/await` in `Script` (no top-level await) |
| `spring()` | `spring({ stiffness: 75, damping: 11, restSpeed: 0.5 })` | Omitting `restSpeed` may cause infinite oscillation |

### The project's own `streak-validate.ts`

`hello-streak-app` includes a project-authored script at `src/scripts/streak-validate.ts`, wired up as `bun run validate`. It is **not** part of the `streak-forge` CLI (that's `streak-forge validate`, a different, narrower check — see [§16](#16-cli-commands-and-build-scripts)). This project script instead checks structural consistency between the sitemap and the filesystem:

1. All `renderId`s are unique
2. Every `dataHandler`/`rootLayout`/widget `type` referenced in the sitemap has a matching file on disk
3. `loadingStrategy` values are valid (only `"lazy"` is recognized)
4. Every sitemap widget has a matching `WidgetPlaceholder` in its layout
5. Handlers have `export default` and (by convention) return `status: 200`
6. Widgets have `export default`, use optional chaining on `props.data`, and don't call React hooks
7. Any local `/images|/assets|/styles` path referenced inside a handler actually exists under `public/`

Exit code `0` = pass, `1` = one or more errors found (warnings don't fail the run). Run it (along with `lint` and `typecheck`) after any structural change, before building.

## 24. Quick-Start Checklist

### New project

- [ ] `bunx create-streak-app` (or install `streak-forge` manually into an existing Bun project)
- [ ] Create `streak.sitemap.json` at the project root
- [ ] Set up `tsconfig.json` with `jsx: "react-jsx"`, **`jsxImportSource: "streak-forge"`**, and `moduleResolution: "bundler"`
- [ ] Set up Tailwind: `tailwind.config.js` + `src/common/styles/input.css`
- [ ] Add build scripts to `package.json`

### New page

- [ ] Add entry to `streak.sitemap.json` with a `renderId` and a `version`
- [ ] Create `src/handlers/YourHandler.ts` — default export, `(metadata, { common }) => {...}`
- [ ] Create `src/layouts/YourLayout.tsx` — default export, full `<html>` doc, `WidgetPlaceholder` for each widget
- [ ] Create each widget in `src/widgets/YourWidget.tsx` — default export, accepts `props.data`
- [ ] Verify every sitemap widget has a matching `WidgetPlaceholder` in the layout
- [ ] Verify every `WidgetPlaceholder` `type` matches the widget filename exactly

### Sharing data across pages (CommonHandler)

- [ ] Create `src/handlers/CommonHandler.ts` — default export, **no arguments**, returns shared data
- [ ] Read it in any page handler via the second argument: `(metadata, { common }) => {...}`
- [ ] Remember: once per `build`, fresh every request in `dev`

### Custom routing (Middleware)

- [ ] Create `src/handlers/Middleware.ts` — default export, `(url, req?) => RenderConfig | undefined`
- [ ] Return `undefined` to fall through to the sitemap's own entry
- [ ] Return a `RenderConfig` to override a listed URL, or to serve a URL not in the sitemap at all

### Adding client interactivity (Script)

- [ ] Add `<Script id="unique-id" options={{ ...serverData }}>` to the widget JSX
- [ ] Write `(gDom: any, options: any) => { ... }` as the child function
- [ ] Confirm all server values are passed via `options` (not closed over) — run `streak-forge validate` to check
- [ ] Use `document.getElementById(...)` to find DOM elements (use stable IDs in JSX)

### Adding deferred content (Dynamic)

- [ ] Wrap deferred content in `<Dynamic id="panel-id">...</Dynamic>`
- [ ] In a `Script`, call `gDom.loadDynamicComponent("panel-id", callback)` on user interaction
- [ ] In the callback, fade in the injected content with `requestAnimationFrame`
- [ ] Start the injected content with `style={{ opacity: 0 }}` for a smooth reveal

### Adding third-party JS (loadPackage)

- [ ] Place the library file in `public/assets/js/yourlib.js`
- [ ] Commit the file to git (do NOT gitignore it)
- [ ] In a `Script`, call `gDom.loadPackage("js/yourlib.js").then(() => { ... })`
- [ ] Access the library as `(gDom as any).LibraryGlobal`

### Adding resource hints (Preload)

- [ ] Add `<Preload href="..." as="style|image|font|script" media="..." />` before the `<link>` or `<img>` tag
- [ ] Use `media=""` for all-screen preloads, or a media query for responsive preloads
